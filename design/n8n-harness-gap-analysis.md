# n8n Agents versus the Langflow Agent Harness

Research date: 2026-09-15. Langflow source reviewed at `90a7dd4069`. This is a research comparison and proposed sequence, not an implementation change.

## The relevant n8n product

The relevant comparison is **n8n Agents and its Agent Builder**, announced on August 5, 2026. It creates an agent as its own project resource, distinct from the existing AI Agent node inside a workflow. The release packages instructions, model, tools, conversation continuity, channels, schedules, publishing, and delegation around that resource. “Harness builder” is a useful description of this direction; the official product name in the sources is Agent Builder. [n8n announcement](https://community.n8n.io/t/introducing-n8n-agents-a-new-way-to-build-agents-you-set-up-once-and-use-anywhere/306323).

This supports our original direction: **project types with an Agent Harness at the center**. The principal gap is the complete life of that agent—reusable capabilities, release, reachability, assessment, and collaboration—around the runtime controls already implemented. The local registry currently registers Flows, Agent Harness, and Tool Pack. [Project types and harness fields](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/builtins.py).

## Recommended next slices

The priorities below are recommendations based on the comparison. “Missing” means missing from the delivered harness experience; it does not mean Langflow lacks every underlying primitive.

Skill Packs, Eval Suites, delegated harnesses, the broader dependency view, and the composable loop are already identified as later work in the [first-delivery acceptance document](/Users/ogabrielluiz/Projects/ideas/agent-harness-building-blocks/FIRST-DELIVERY-ACCEPTANCE.md). The comparison helps order that work; it does not replace the agreed project-types direction.

## What we should preserve

Our current delivery already includes enforceable lifecycle hooks, context processing, compaction, permissions and approval continuation, reviewed transitive dependencies, evidence/configuration reports, and portable compositions. These belong in the harness model and should survive all subsequent UI simplification. [Hooks](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/hooks.py), [context](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/context.py), [compaction](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/compaction.py), [permissions](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/permissions.py).

The latest Instructions implementation uses normal Prompt Template Message outputs. The new taxonomy should continue to reuse Langflow's existing types and components instead of introducing adapter components solely to satisfy an artificial type distinction. [Instructions binding](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/bindings.py).

The authoring gap is specifically an inspectable and editable harness contract surface with example inputs, expected outputs, and preflight checks. It is not the absence of runtime tool argument schemas or structured Agent outputs, both of which already exist. [Tool schema capture](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/projects/run_configuration.py:149), [structured Agent output](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/components/models_and_agents/agent.py:1034).

Reviewed snapshots and run evidence also do not constitute a promise of permanent, complete root-source historical replay. A future release/evaluation design needs explicit retention and replay behavior rather than assuming current snapshot storage provides that guarantee. [Current acceptance and limits](/Users/ogabrielluiz/Projects/ideas/agent-harness-building-blocks/FIRST-DELIVERY-ACCEPTANCE.md).

Do not mistake a missing harness tab for a missing platform: memory, knowledge, flow deployment/versioning, A2A, MCP client/server, and builder tools already have infrastructure in this codebase. The work is to expose a coherent contract and lifecycle around those facilities, not replace them. Examples include [session history loading](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/components/models_and_agents/agent.py:1105), [deployment artifact snapshots](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/backend/base/langflow/services/deployment_artifacts/builder.py:814), and [flow builder tools](/Users/ogabrielluiz/Projects/langflow-wt-lfx-proj/src/lfx/src/lfx/mcp/flow_builder_tools).

## Lessons from the wider n8n workflow platform

These capabilities are documented for n8n workflows or AI nodes. They should not automatically be credited to the new Agent Builder UI.

| Capability | Useful lesson | Limits and qualification |
| --- | --- | --- |
| Typed sub-workflow inputs | Define fields/types or provide a JSON example; the caller's input form is populated from that definition. [Sub-workflow trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflowtrigger.md) | An “accept all data” mode also exists, leaving validation to the sub-workflow. For us, use explicit contracts for hooks, skills, delegates, and evaluation inputs. |
| Tool arguments | A field can be fixed or supplied by the model; `$fromAI` provides key, description, type, and default. [AI parameters](https://docs.n8n.io/build/integrate-ai/ai-examples/use-ai-for-parameters.md) | This is a better authoring affordance than expecting users to infer which fields the model controls. It is documented for connected app tools, not every node. |
| Structured output | A format switch exposes an output-parser attachment; schema can be generated from JSON or authored directly. [Parser](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.outputparserstructured.md) | JSON-example generation makes every field required; `$ref` is unsupported. n8n warns agent parsing can be unreliable and suggests a separate formatting chain. A parser is not evidence of factual correctness. [Parser limitations](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.outputparserstructured/common-issues.md) |
| Human review | Tool-specific approval can be routed to a different channel; reviewers see tool name and proposed parameters. Nested agent-tool approvals are documented. [Human review](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md) | We have approvals already. The remaining opportunities are routing, team review, and clear propagation through delegated harnesses. |
| Debugging from past runs | Copy previous execution data into the current editor and pin it to reproduce a failure with a changed workflow. [Debug executions](https://docs.n8n.io/build/understand-workflows/understand-executions/debug-executions.md) | This is not a promise of deterministic, side-effect-free historical replay. Our immutable source provenance and a safe “turn this run into an eval case” action should complement each other. |
| Model fallback and guardrails | AI Agent Tool exposes a backup-model connection; Guardrails provides checking/sanitization with fail routing. [Fallback](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolaiagent.md), [Guardrails](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.guardrails.md) | These are explicit workflow controls. We should expose useful policies through our existing harness/runtime contracts, with recorded outcomes, rather than only suggest them in instructions. |

## Availability and evidence boundaries

- The new Agents product remains **Preview**. Self-hosted support starts at 2.32.3 Beta; self-hosted Enterprise and queue mode are not supported by the current documentation. Self-hosted knowledge requires a Daytona sandbox, and episodic memory requires an OpenAI credential. [Current availability](https://docs.n8n.io/build/build-and-manage-agents#self-hosted).
- Current n8n Assistant is Preview on Cloud Starter/Pro and self-hosted Community/Registered Community/Business; Enterprise access is not general availability. Its generation consumes credits. [Assistant availability](https://docs.n8n.io/build/ways-of-building-workflows/n8n-assistant.md).
- Light evaluations and debug-from-history have plan/registration conditions. Metric evaluations are generally Cloud Pro/Enterprise and self-hosted Enterprise, with a single-workflow allowance for Registered Community and Starter. [Quick evaluations](https://docs.n8n.io/build/integrate-ai/test-and-improve-ai-workflows/run-quick-evaluations.md), [metric evaluation availability](https://docs.n8n.io/build/integrate-ai/test-and-improve-ai-workflows/use-metrics-to-measure-quality.md).
- Current MCP documentation adds agent management and preview execution from 2.34.0. That is newer than the launch announcement's statement about outside callers; management/preview via MCP should not be conflated with a general published-agent production API. [MCP reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference.md#agent-management).
- n8n's public SDK source exposes input/output guardrails, structured output, evaluation, checkpointing, memory, deferred tools, and concurrency. This proves implementation vocabulary exists, not that every control is shipped in the Agent Builder UI. We should not claim n8n lacks runtime primitives simply because the introductory page omits them. [SDK builder interface](https://github.com/n8n-io/n8n/blob/master/packages/%40n8n/agents/src/types/sdk/agent-builder.ts).

## A concrete proof for our next delivery

Keep the research-agent workflow, but use it to prove the taxonomy:

1. An Agent Harness attaches a **Research Skill Pack**, an existing Tool Pack, and a knowledge resource.
2. An **Eval Suite** tests sourced claims, policy behavior, and budgets against an exact reviewed composition; a saved failure can become another test case.
3. The user previews the candidate, reviews its evaluation results, and releases that complete composition.
4. The harness delegates source verification to a second released Harness, with linked inputs, results, permissions, and evidence.
5. The same released harness can later be invoked interactively or on a schedule without duplicating its definition.

This sequence is a proposed acceptance path. Deliver it on a small number of capability branches—skills, evaluations, release lifecycle, delegation—while integrating existing memory, knowledge, and deployment facilities as each slice needs them.
