In general, environment variables, like `LANGFLOW_PORT` or `LANGFLOW_LOG_LEVEL`, configure how Langflow runs.
These are broad settings that apply to your entire Langflow deployment.

In contrast, global variables are user-defined values stored in Langflow's database for use in flows, such as `OPENAI_API_KEY`.
Langflow can also source global variables from environment variables.
For more information, see [Langflow global variables](/configuration-global-variables).

## Configure environment variables for Langflow OSS

Langflow recognizes [supported environment variables](#supported-variables) from the following sources:

- Environment variables set in your terminal.
- Environment variables imported from a `.env` file when starting Langflow.
- Environment variables set with the [Langflow CLI](./configuration-cli), including the `--env-file` option and direct options, such as `--port`.

You can choose to use one or more of these sources.

### Precedence {#precedence}

If the same environment variable is set in multiple places, the following hierarchy applies:

1. Langflow CLI options override all other sources.
2. The `.env` file overrides system environment variables.
3. System environment variables are used only if not set elsewhere.
When running a Langflow Docker image, the `-e` flag can be used to set additional system environment variables.

For example:

* If you set `LANGFLOW_PORT=8080` in your system environment and `LANGFLOW_PORT=7860` in `.env`, Langflow uses `7860` from `.env`.
* If you use the Langflow CLI to run `langflow run --env-file .env --port 9000`, and you set `LANGFLOW_PORT=7860` in `.env`, then Langflow uses `9000` from the CLI option.

### Set environment variables in your terminal {#configure-variables-terminal}

Run the following commands to set environment variables for your current terminal session:

<Tabs>
<TabItem value="linux-macos" label="Linux or macOS" default>

```bash
export VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="windows" label="Windows">

```
set VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="docker" label="Docker">

```bash
docker run -it --rm \
    -p 7860:7860 \
    -e VARIABLE_NAME='VALUE' \
    langflowai/langflow:latest
```

</TabItem>
</Tabs>

When you start Langflow, it looks for environment variables that you've set in your terminal.
If it detects a supported environment variable, then it automatically adopts the specified value, subject to [precedence rules](#precedence).

### Import environment variables from a .env file {#configure-variables-env-file}

1. If Langflow is running, quit Langflow.

2. Create a `.env` file, and then open it in your preferred editor.

3. Define [Langflow environment variables](#supported-variables) in the `.env` file.

    <details>
    <summary>Example: .env</summary>

    ```text
    DO_NOT_TRACK=True
    LANGFLOW_AUTO_LOGIN=False
    LANGFLOW_AUTO_SAVING=True
    LANGFLOW_AUTO_SAVING_INTERVAL=1000
    LANGFLOW_BACKEND_ONLY=False
    LANGFLOW_BUNDLE_URLS=["https://github.com/user/repo/commit/hash"]
    LANGFLOW_CACHE_TYPE=async
    LANGFLOW_COMPONENTS_PATH=/path/to/components/
    LANGFLOW_COMPONENTS_INDEX_PATH=/path/to/component_index.json
    LANGFLOW_CONFIG_DIR=/path/to/config/
    LANGFLOW_DATABASE_URL=postgresql://user:password@localhost:5432/langflow
    LANGFLOW_DEV=False
    LANGFLOW_FALLBACK_TO_ENV_VAR=False
    LANGFLOW_HEALTH_CHECK_MAX_RETRIES=5
    LANGFLOW_HOST=localhost
    LANGFLOW_LANGCHAIN_CACHE=InMemoryCache
    LANGFLOW_MAX_FILE_SIZE_UPLOAD=10000
    LANGFLOW_MAX_ITEMS_LENGTH=100
    LANGFLOW_MAX_TEXT_LENGTH=1000
    LANGFLOW_LOG_LEVEL=error
    LANGFLOW_OPEN_BROWSER=False
    LANGFLOW_PORT=7860
    LANGFLOW_REMOVE_API_KEYS=False
    LANGFLOW_SAVE_DB_IN_CONFIG_DIR=True
    LANGFLOW_SECRET_KEY=somesecretkey
    LANGFLOW_STORE_ENVIRONMENT_VARIABLES=True
    LANGFLOW_SUPERUSER=adminuser
    LANGFLOW_SUPERUSER_PASSWORD=adminpass
    LANGFLOW_WORKER_TIMEOUT=300
    LANGFLOW_WORKERS=3
    ```

    For additional examples, see [`.env.example`](https://github.com/langflow-ai/langflow/blob/main/.env.example) in the Langflow repository.

    </details>

4. Save and close `.env`.

5. Start Langflow with your `.env` file:

    <Tabs>
    <TabItem value="local" label="Local" default>

    ```bash
    uv run langflow run --env-file .env
    ```

    </TabItem>
    <TabItem value="docker" label="Docker">

    ```bash
    docker run -it --rm \
        -p 7860:7860 \
        --env-file .env \
        langflowai/langflow:latest
    ```

    </TabItem>
    </Tabs>

    If your `.env` file isn't in the same directory, provide the path to your `.env` file.

On startup, Langflow imports the environment variables from your `.env` file, as well as any others that you set in your terminal, and then adopts their specified values.

## Set environment variables for Langflow Desktop

Environment variables set in your terminal aren't automatically available to GUI-based applications like Langflow Desktop when you launch them from the Windows or macOS GUI.

To modify environment variables for Langflow Desktop, set environment variables in a Desktop `.env` file, and then restart the app.

<Tabs>
<TabItem value="macos" label="macOS" default>

To modify the macOS `.env` file, do the following:

1. Create or edit `~/.langflow/data/.env`.
2. Add your Langflow environment variables, for example:

    ```text
    LANGFLOW_LOG_LEVEL=info
    LANGFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart Langflow Desktop.

</TabItem>
<TabItem value="windows" label="Windows .env file">

To modify the Windows `.env` file, do the following:

1. Create or edit `%APPDATA%\com.LangflowDesktop\data\.env`.
2. Add your Langflow environment variables, for example:

    ```text
    LANGFLOW_LOG_LEVEL=info
    LANGFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart Langflow Desktop.

</TabItem>
<TabItem value="windows-user-vars" label="Windows user environment variables">

Windows supports two sources for Langflow Desktop environment variables: a Langflow application `.env` file, and Windows user environment variables.

The `.env` file at `%APPDATA%\com.LangflowDesktop\data\.env` is the recommended approach, but
Windows user variables are useful for single-sourcing API keys between Langflow and other Windows applications.
If the same variable is defined in both the Langflow application `.env` file and as a Windows user environment variable, the `.env` file takes precedence.

To modify the Windows user environment variables, do the following:

1. Press <kbd>Win + R</kbd>, enter `sysdm.cpl`, and then press <kbd>Enter</kbd>.
2. Click the **Advanced** tab, and then click **Environment Variables**.
3. In **User variables**, click **New**.
4. Enter the variable name, such as `OPENAI_API_KEY`, and its value.
5. Click **OK**, and then **restart Langflow Desktop**.

</TabItem>
</Tabs>

## Supported environment variables {#supported-variables}

The following sections provide information about specific Langflow environment variables.

### Authentication and security

See [API keys and authentication](/api-keys-and-authentication).

The following variables configure SSO and cookie behavior. SSO requires an SSO plugin. Langflow includes these settings, but doesn't include an SSO provider.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_COOKIE_DOMAIN` | String | Not set | The `Domain` attribute for cookies that Langflow sets. If not set, cookies are scoped to the host that set them. |
| `LANGFLOW_EXTERNAL_AUTH_GROUP_RECONCILE_INTERVAL_SECONDS` | Integer | `60` | Minimum number of seconds between group reconciliations with the external identity provider when a user's groups haven't changed. Changed groups are always reconciled immediately. Set to `0` to reconcile on every request. |
| `LANGFLOW_SSO_CONFIG_FILE` | String | Not set | Path to the SSO configuration file, in YAML format. Required when `LANGFLOW_SSO_ENABLED` is `true`. |
| `LANGFLOW_SSO_ENABLED` | Boolean | `False` | Whether to enable SSO authentication. Requires an SSO plugin. |
| `LANGFLOW_SSO_PROVIDER` | String | `jwt` | The SSO provider type: `jwt`, `oidc`, `saml`, or `ldap`. |
| `LANGFLOW_SSO_REDIRECT_URL` | String | Not set | The URL to redirect users to after SSO authentication. Must be a relative URL on the same origin, such as `/flows`. Absolute URLs are rejected. |

### MCP servers {#mcp}

See [Use Langflow as an MCP server](/mcp-server).

The following variables configure how Langflow launches and supervises MCP servers.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_MCP_BASE_URL` | String | Not set | The externally reachable base URL that Langflow uses to build MCP server URLs, such as `https://langflow.example.com`. Set this for multi-pod deployments where the server binds to `0.0.0.0` but clients must reach it through a gateway or service address. If not set, Langflow builds URLs from `LANGFLOW_HOST` and `LANGFLOW_PORT`, and the visual editor uses the browser's current origin. |
| `LANGFLOW_MCP_COMPOSER_ENABLED` | Boolean | `True` | Whether to start the MCP Composer service. If `false`, Langflow doesn't start MCP Composer. |
| `LANGFLOW_MCP_COMPOSER_VERSION` | String | `==0.1.0.8.10` | The version constraint for MCP Composer when it runs through `uvx`, in [PEP 440](https://peps.python.org/pep-0440/) format. |
| `LANGFLOW_MCP_SDK_CONSTRAINT` | String | `mcp~=1.28` | The MCP SDK requirement that Langflow passes to `uvx --with` when it launches an MCP server through `uvx`. Each `uvx` server runs in its own environment, so Langflow's own `mcp` version doesn't apply there. Set to an empty string to turn off this requirement. |
| `LANGFLOW_MCP_SERVER_ALLOWED_PACKAGES` | String | Not set | Comma-separated list of packages that MCP stdio servers can run with `npx` or `uvx`. If set, only these exact package names can be downloaded and run. Version specifiers are allowed, but don't change which package is matched. If empty, all `npx` and `uvx` packages are blocked. If not set, any package can run. |
| `LANGFLOW_MCP_SERVER_INTERPRETER_HARDENING` | Boolean | `False` | If `true`, rejects MCP stdio servers that run Python, Node.js, or a shell directly, such as `python <uploaded-file>`. The command allowlist alone can't make these commands safe. Package runners such as `npx` and `uvx` are still allowed. See [Component hardening for untrusted users](/api-keys-and-authentication#multi-tenant-component-hardening). |
| `LANGFLOW_MCP_SESSION_CLEANUP_INTERVAL` | Integer | `120` | How often, in seconds, Langflow checks for and closes idle MCP sessions. |
| `LANGFLOW_MCP_SESSION_IDLE_TIMEOUT` | Integer | `400` | How long, in seconds, an MCP session can stay idle before Langflow closes it. |
| `LANGFLOW_MCP_SSE_ENABLED` | Boolean | `True` | Whether to serve the legacy SSE transport for Langflow's MCP server. If `false`, the SSE endpoints return `404` and only the Streamable HTTP transport is available. |
| `LANGFLOW_SKIP_MCP_AUTO_INIT` | Boolean | `False` | If `true`, Langflow doesn't configure project MCP servers at startup. By default, Langflow checks every project's MCP server configuration at startup, which can launch `uvx mcp-proxy` and open outbound connections. On offline or firewalled hosts, this can delay startup, so set this to `true` for air-gapped deployments. |

### Background jobs and workflow execution

The following variables configure how Langflow runs flows in the background, and how long a single run can take.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_BACKGROUND_HEARTBEAT_INTERVAL_S` | Float | `15.0` | How often, in seconds, a running background job reports that it's still alive. Keep this well below `LANGFLOW_BACKGROUND_LEASE_TTL_S` so that a brief stall doesn't cause the job to be treated as failed. Must be greater than `0`. |
| `LANGFLOW_BACKGROUND_INPUT_DEADLINE_S` | Float | Not set | Maximum time, in seconds, a background run can wait for human input before it's marked as failed. Time spent waiting doesn't count toward `LANGFLOW_BACKGROUND_JOB_TIMEOUT`. If not set, a run can wait indefinitely. |
| `LANGFLOW_BACKGROUND_JOB_TIMEOUT` | Float | Not set | Maximum time, in seconds, a single background job can run before it's marked as timed out. If not set, background jobs don't time out. |
| `LANGFLOW_BACKGROUND_LEASE_TTL_S` | Float | `45.0` | How long, in seconds, a running background job can go without reporting that it's alive before Langflow treats it as abandoned and fails or requeues it. |
| `LANGFLOW_BACKGROUND_MAX_CONCURRENCY` | Integer | `5` | Maximum number of background jobs that run at the same time in each Langflow process. Additional jobs wait in a queue. The default is low so that background jobs don't slow down API requests. Increase it for dedicated worker processes. Must be greater than `0`. |
| `LANGFLOW_BACKGROUND_WATCHDOG_INTERVAL_S` | Float | `15.0` | How often, in seconds, Langflow checks for background runs that have passed `LANGFLOW_BACKGROUND_INPUT_DEADLINE_S`, and, in Redis-backed multi-worker deployments, recovers jobs left behind by a worker that stopped. Must be greater than `0`. |
| `LANGFLOW_EXECUTOR_KIND` | String | `in-process` | The executor that runs flows. Must match the name of a registered executor. |
| `LANGFLOW_MAX_INGESTION_TIMEOUT_SECS` | Integer | `600` | Maximum time, in seconds, a [memory base](/memory-bases) ingestion job waits for other ingestion jobs in the same session to finish. If the wait takes longer, the job is marked as timed out. |
| `LANGFLOW_WORKFLOW_EXECUTION_TIMEOUT` | Integer | `300` | Maximum time, in seconds, a single v2 workflow run can take when a client is waiting for the result. Synchronous runs return a `408` error, and streaming and public runs send an error event. Doesn't apply to background runs, which use `LANGFLOW_BACKGROUND_JOB_TIMEOUT` instead. |

### Flow cache and warm registry

The warm registry keeps recently used flows in memory so that Langflow doesn't need to rebuild them on every run. The following variables configure the warm registry and Langflow's in-memory caches.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_CACHE_DIR` | String | Not set | Directory where Langflow stores flow change events, such as components being added or connected, so that multiple workers can share them. If not set, Langflow uses a temporary directory. |
| `LANGFLOW_CACHE_EXPIRE` | Integer | `3600` | How long, in seconds, entries stay in the in-memory caches. For the Redis cache, use `LANGFLOW_REDIS_CACHE_EXPIRE` instead. |
| `LANGFLOW_WARM_RECONCILE_INTERVAL` | Float | `20.0` | How often, in seconds, each worker syncs its warm registry with the flows in the database. Deployed or deleted flows can take up to this long to reach every worker. Only used when `LANGFLOW_WARM_REGISTRY_ENABLED` is `true`. |
| `LANGFLOW_WARM_REGISTRY_ENABLED` | Boolean | `False` | Whether to keep recently used flows in memory on each worker. |
| `LANGFLOW_WARM_REGISTRY_MAX_ENTRIES` | Integer | `128` | Maximum number of flows each worker keeps in memory. |
| `LANGFLOW_WARM_REGISTRY_MAX_FLOW_BYTES` | Integer | `2000000` | Maximum size, in bytes, of a single flow that can be kept in memory. Larger flows aren't kept in memory. |
| `LANGFLOW_WARM_REGISTRY_MAX_TOTAL_BYTES` | Integer | `32000000` | Maximum total size, in bytes, of all flows each worker keeps in memory. |
| `LANGFLOW_WARM_REGISTRY_PRELOAD_LIMIT` | Integer | `0` | Maximum number of flows each worker loads into memory at startup. With the default of `0`, flows are loaded only after they're first run. |

### Knowledge bases and file ingestion

The following variables configure which directories knowledge bases can ingest files from, and the maximum size of ingested files.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_DIRECTORY_COMPONENT_ALLOWED_ROOTS` | List[String] | `[]` | Comma-separated list of additional directories that the legacy **Directory** component can read from. The component can always read from the Langflow working directory and its subdirectories. |
| `LANGFLOW_KB_ALLOWED_FOLDER_ROOTS` | List[String] | `[]` | Comma-separated list of directories that knowledge bases can ingest folders from, such as `/srv/docs,/data/shared`. If empty, knowledge bases can't ingest folders. |
| `LANGFLOW_KB_DISK_RECONCILE_ENABLED` | Boolean | `False` | If `true`, Langflow scans the knowledge bases directory at startup and registers knowledge base folders that aren't in the database, such as folders created by an earlier Langflow version. |
| `LANGFLOW_KB_FOLDER_MAX_FILE_SIZE_BYTES` | Integer | `26214400` | Maximum size, in bytes, of a single file ingested from a folder into a knowledge base. The default is 25 MB. Requests can't override this limit. |

| Variable | Format | Default | Description |

### Sandbox backends {#langflow-sandbox}

These variables control optional execution backends for the [**Python Interpreter** Component](/python-interpreter#sandbox) and the legacy Python REPL tool.
The `exec-sandbox` backend is not included in a default `uv pip install langflow` installation; install `langflow[sandbox]` to use it.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|

When a configured backend is unavailable, execution fails with an error instead of falling back to in-process execution. |
| `LANGFLOW_SANDBOX_TIMEOUT_SECONDS` | Integer | `30` | Wall-clock limit for one sandboxed execution (1-300 seconds). | `LANGFLOW_SANDBOX_MEMORY_MB` | Integer | `192` | Guest VM memory for sandboxed executions, in MB (minimum 128). Only used when `LANGFLOW_SANDBOX_BACKEND` is not `none`. |
| `LANGFLOW_SANDBOX_ALLOW_NETWORK` | Boolean | `False` | Whether sandboxed code may access the network. The default runs the microVM fully offline. | `LANGFLOW_SANDBOX_ALLOWED_DOMAINS` | String | Not set | Comma-separated list of domains sandboxed code may reach when network access is enabled. Treat like an SSRF allow-list: prefer narrow, fully-qualified domains. Only used when `LANGFLOW_SANDBOX_BACKEND` is not `none`. |

| `LANGFLOW_SANDBOX_BACKEND_PLUGINS` | String | Not set | Comma-separated names of out-of-tree sandbox backends that may load, from the `lfx.sandbox_backends` entry point group — see [Sandbox backends](../Deployment/sandbox-backends.mdx). | `LANGFLOW_FS_FLOWS_POLLING_INTERVAL` | Integer | `10000` | How often, in milliseconds, Langflow syncs flows from the file system. |
| `LANGFLOW_WEBHOOK_POLLING_INTERVAL` | Integer | `0` | How often, in milliseconds, the visual editor polls for webhook updates. The default of `0` turns off polling, because webhook updates are already sent in real time. |
| `LANGFLOW_MAX_FLOW_VERSION_ENTRIES_PER_FLOW` | Integer | `50` | Maximum number of saved versions to keep for each flow. When a new version is saved, the oldest versions beyond this limit are deleted. Lowering this value doesn't delete versions until the next version is saved. |
| `LANGFLOW_MODEL_PROVIDER_POLICY_REFRESH_INTERVAL_S` | Float | `10.0` | How often, in seconds, each worker reloads the model provider policy. Policy changes can take up to this long to reach every worker. |

### Hide UI elements with embedded mode {#embedded-mode}

When you embed the Langflow visual editor in another application, such as an iframe within a host portal, you can hide UI elements that are usually visible in the visual editor.

The embedded mode environment variables control which UI elements appear in the visual editor.
Embedded mode controls UI visibility only, and does not block API endpoints or deploy Langflow.

Embedded mode is distinct from the [embedded chat widget](/concepts-publish#embedded-chat-widget), which embeds a single flow's chat UI in a website.

When `LANGFLOW_EMBEDDED_MODE=true`, Langflow hides the following buttons in the UI:

* **Logout**
* **New project**
* **New flow**
* **Starter projects**

You can hide individual elements without enabling the umbrella flag.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `LANGFLOW_EMBEDDED_MODE` | Boolean | `False` | Umbrella flag for embedded or iframe deployments. When `true`, hides standalone UI elements: logout, new project, new flow, and starter projects. Individual hide flags can also be set without enabling this flag. |
| `LANGFLOW_HIDE_LOGOUT_BUTTON` | Boolean | `False` | If `true`, hides the logout button in the account menu. Automatically enabled when `LANGFLOW_EMBEDDED_MODE=true`. |
| `LANGFLOW_HIDE_NEW_PROJECT_BUTTON` | Boolean | `False` | If `true`, hides the new project/folder button in the sidebar. Automatically enabled when `LANGFLOW_EMBEDDED_MODE=true`. |
| `LANGFLOW_HIDE_NEW_FLOW_BUTTON` | Boolean | `False` | If `true`, hides the new flow button in the header. Automatically enabled when `LANGFLOW_EMBEDDED_MODE=true`. |
| `LANGFLOW_HIDE_STARTER_PROJECTS` | Boolean | `False` | If `true`, hides the starter projects tab in the templates modal. Does not affect database seeding of starter projects. Automatically enabled when `LANGFLOW_EMBEDDED_MODE=true`. |
| `LANGFLOW_HIDE_GETTING_STARTED_PROGRESS` | Boolean | `False` | If `true`, hides the getting-started onboarding progress UI. Not automatically enabled when `LANGFLOW_EMBEDDED_MODE=true`. |
