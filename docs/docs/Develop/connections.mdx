A **Connection** is a reusable credential that your flows can take scoped actions with.
To connect Google Workspace, Microsoft 365, Slack, Jira Cloud, or GitHub, follow the steps below.

Only the **Authorize** step differs between different connections.

## Prerequisite

* Sign in to the Langflow server. Any signed-in user can create their own connection.
* For Google, Microsoft, Slack, or Jira, an operator must configure the provider's OAuth registration before users can connect an account.
  See [Configure connection OAuth](./connection-oauth).
  Jira requires the Atlassian app and site UUID on [Jira Cloud components](./bundles-jira#configure-the-atlassian-app).
* For GitHub, create a GitHub App installation token first.
  For more information, see [GitHub components](./bundles-github#create-an-installation-token).

## Add a connection

1. In the Langflow header, click your profile icon, and then select **Settings**.
2. Click **Connections**.
3. Click <Icon name="Plus" aria-hidden="true" /> **Add connection**.
4. Select the **Provider**.
5. Enter a **Handle** and a **Display name**.
   The handle is the stable name stored with a flow, such as `work` in `google/work`.
   It travels with an exported flow and cannot be renamed.
   The display name is the label in Langflow, and it can be renamed.
6. Authorize the provider.

   <Tabs groupId="integration" queryString="integration">
   <TabItem value="google" label="Google Workspace" default>

   In **Scopes to request**, select the permissions the flow needs, such as `gmail.send` for [**Gmail: Send Email**](./bundles-google).
   Click **Continue** and finish consent in Google.
   The connection acts as the account that authorized it, including when another user selects an instance-shared connection.
   A handle of `work` is stored as `google/work`.

   </TabItem>
   <TabItem value="microsoft" label="Microsoft 365">

   In **Scopes to request**, select the short permission names the flow needs, such as `Mail.Send`.
   Click **Continue** and finish consent in Microsoft.
   The connection acts as the account that authorized it.
   A handle of `work` is stored as `microsoft/work`.

   </TabItem>
   <TabItem value="slack" label="Slack">

   Choose whether the connection acts as the account that authorizes it, or as a Slackbot.
   In **Scopes to request**, select the scopes the actions need.
   Click **Continue** and finish consent in Slack.
   A handle of `work` is stored as `slack/work`.

   </TabItem>
   <TabItem value="jira" label="Jira Cloud">

   Keep `offline_access`, `read:jira-work`, and `read:jira-user` selected.
   Add `write:jira-work` when the flow creates, edits, or transitions issues.
   Click **Continue** and authorize the configured Jira site.
   Langflow requires the refresh token from that consent.
   A handle of `work` is stored as `jira/work`.

   </TabItem>
   <TabItem value="github" label="GitHub">

   Paste the installation access token and the expiration GitHub reported.
   GitHub has no consent window on this step.
   Select **Allow background runs** when this connection will arm triggers.
   A handle of `work` is stored as `github/work`.
   The token expires after one hour. **Reconnect** keeps the same handle when you paste a replacement.

   </TabItem>
   </Tabs>

7. Click **Done**.
   If **Continue** is unavailable and Langflow reports that no OAuth registration is configured, ask the server administrator to configure it before you retry.
8. For Google, Microsoft, Slack, or Jira, open <Icon name="Ellipsis" aria-hidden="true" /> **Actions** on the saved connection and select **Allow scheduled and deployed runs** when this connection will run triggers.

## Use a connection in a flow

1. Add a component that uses the Connection, such as [**Gmail: Send Email**](./bundles-google), a [Microsoft 365 component](./bundles-microsoft), a [Slack component](./bundles-slack), a [Jira Cloud component](./bundles-jira), or a [GitHub component](./bundles-github).
2. In the component's Connection field, select the Connection.
   The field shows the scope that action requires.
   The flow stores the handle. The token stays on the server.

## Share a connection with other users

If you're logged in as a Langflow superuser, the **Add connection** pane includes an additional **Share with the whole instance** checkbox.
Enable this box to share the connection with all users on the Langflow server.
The connection appears in users' **Instance** tab.

## Include connections with exported flows

An exported flow keeps each connection field as its handle, such as `google/work`.
The file does not include the token, account, or scopes.

To transfer a flow connection from one server to another, do the following:

1. Export the flow.
   On the **Projects** page, click <Icon name="Ellipsis" aria-hidden="true" /> **More** on the flow, and then select **Export**.
   Langflow downloads a JSON file. Each connection field in the JSON file includes the connection handle.

2. Import the flow on the other Langflow server.
   On the new server's **Projects** page, click <Icon name="Upload" aria-hidden="true" /> **Upload a flow**, and then select the JSON file.

3. On the new server, repeat [Add a connection](#add-a-connection) for the same provider and handle.

4. Run the flow.
   The flow uses the saved handle.

## Manage connections

Open <Icon name="Ellipsis" aria-hidden="true" /> **Actions** on the row.

* **Check credential** tests the stored credential. It is available after the connection has one.
* **Authorize** or **Reconnect** starts consent again. Scopes the connection already holds stay selected. Check another scope to add it, or clear one to drop it. A pending connection offers **Authorize**. A connection that already completed consent offers **Reconnect**. For GitHub, **Reconnect** asks for a new installation token and its expiration.
* **Rename** changes the display name. The handle stays the same, so flows that reference it keep working.
* **Allow scheduled and deployed runs** lets the owner opt a user-owned connection into unattended execution.

    Enable this setting for owner-based webhooks, deployments, and resumed jobs that use a user-owned connection. For example, `POST /api/v1/webhook/FLOW_ID` runs the flow as the flow's owner and resolves connections for that owner.

    The authenticated playground and `POST /api/v1/run` endpoints act as the signed-in caller. They can use the caller's own connections, connections shared with the caller, or instance connections without enabling this setting.

    A [public playground link](/concepts-playground#share-a-flows-playground) or an [A2A agent](/a2a-server) cannot use a connection, whether this setting is enabled or disabled.
* **Revoke** removes the stored credential. The row stays, with status **Revoked**, and later runs fail until someone authorizes the connection again.
* **Delete** removes the connection. It is available after the credential is gone, so revoke the connection first, or delete it while it is still **Pending**.

Revoking a Google connection authorized through OAuth sign-in also asks Google to revoke the token.
For Slack, Langflow asks Slack to revoke the stored token whether you used OAuth sign-in or **Paste a token**.
The notification confirms when the provider revoked the token. If provider revocation fails or is unavailable,
it says that the credential was only removed from Langflow and directs you to revoke it in the provider's settings.
For a Slack Socket Mode app-level token (`xapp-`), use **Basic Information > App-Level Tokens** in the Slack app's settings if Slack rejects the revocation request.
Microsoft Entra has no per-grant revocation endpoint for this flow, so an administrator removes the app's consent in Entra when upstream revocation is required.
For the provider differences, see [Provider revocation and token rotation](./connection-oauth#provider-revocation-and-token-rotation).
