`createos` is one of the backends registered with Langflow's
[sandbox backend layer](./sandbox-backends.mdx). It runs each code execution in
a throwaway [Firecracker](https://firecracker-microvm.github.io/) microVM on the
CreateOS control plane, instead of running it inside the Langflow process.

Use it when you want hardware isolation for user-authored code but the Langflow
host has no hypervisor to give you. Managed Kubernetes node pools usually do not
expose `/dev/kvm`, which is the case the local
[`exec-sandbox`](../Develop/environment-variables.mdx) backend refuses to run in.

## What it covers

The same two components the `exec-sandbox` backend covers:

* [**Python Interpreter**](../Components/python-interpreter.mdx)
* The legacy **Python REPL** tool

It does **not** cover custom components, the Langflow Assistant's generated
code, code-running agents such as [**CodeAct**](../Components/bundles-codeagents.mdx), or MCP
stdio servers. To block those, see
[Component hardening for untrusted users](../Develop/api-keys-and-authentication.mdx#multi-tenant-component-hardening).

## Set it up

1. Get an API key from [createos.nodeops.network/profile](https://createos.nodeops.network/profile).

2. Set two variables:

   ```bash
   LANGFLOW_SANDBOX_BACKEND=createos
   CREATEOS_SANDBOX_API_KEY=<your key>
   ```

3. Restart Langflow. The backend verifies the key once on first use. If the key
   is missing or the control plane is unreachable, code execution fails with an
   error. It never falls back to running in-process.

That is the whole setup. Nothing is installed on the Langflow host, and no
hypervisor is required there.

## How one execution works

1. A VM is created with the configured shape, image, and network policy.
2. The egress policy CreateOS stored is compared against what was requested. A
   mismatch refuses the run before any code is uploaded.
3. The code is uploaded to `/workspace/main.py` in the guest.
4. `python3 /workspace/main.py` runs, and its output is streamed back.
5. The VM is deleted.

Nothing survives between two executions unless you turn sessions on. A cold
execution measured end to end against the live control plane takes about 1.0 s
(0.87-2.16 s over five runs at the `s-2vcpu-4gb` default), so a fresh VM per
execution is practical for a component a person triggers.

Deletion is asynchronous: the control plane accepts the request and moves the
sandbox to `destroying`, and the host reclaims it shortly after. If the delete
never lands — the Langflow process is killed mid-run, or the request is lost —
the VM pauses itself once idle rather than running indefinitely. That idle
window is always set longer than `LANGFLOW_SANDBOX_TIMEOUT_SECONDS`, so it can
only catch an abandoned VM and never interrupts a running execution.

## Sizing

A CreateOS shape fixes vCPU as well as memory, so it cannot be derived from
`LANGFLOW_SANDBOX_MEMORY_MB` alone.

* The default shape is `s-2vcpu-4gb`.
* `LANGFLOW_SANDBOX_MEMORY_MB` acts as a **floor**. It can raise the shape but
  never shrink it, so its `192` default does not produce a 192 MB VM.
* `CREATEOS_SANDBOX_SHAPE` pins an exact shape. A shape that is unknown, or
  smaller than the configured memory, refuses the run rather than quietly giving
  you less.

List the catalog with `curl https://api.sb.createos.sh/v1/shapes`.

## Network policy

By default the sandbox reaches no routable destination.
`LANGFLOW_SANDBOX_ALLOW_NETWORK` and `LANGFLOW_SANDBOX_ALLOWED_DOMAINS` control
the rest.

:::warning
"No network" is not literally true, and the difference matters if you attach
storage. CreateOS always permits link-local traffic (`169.254.0.0/16`) to the
sandbox, whatever the egress policy says. That range carries the VM metadata
service, which responds to guest HTTP requests even under the default deny-all
policy — verified against a live sandbox.

Langflow does not attach CreateOS disks, so nothing Langflow puts in a sandbox
is exposed there. But if you attach an S3 disk to a sandbox by other means, its
credentials are published to that metadata service in plaintext, and sandboxed
code can read them. Do not treat the default policy as a guarantee that
untrusted code sees nothing at all.
:::

:::warning
`LANGFLOW_SANDBOX_ALLOW_NETWORK=true` with an empty
`LANGFLOW_SANDBOX_ALLOWED_DOMAINS` grants **unrestricted** outbound access under
this backend. The `exec-sandbox` backend instead keeps a package-registry-only
default; CreateOS has no equivalent built-in list. Always set an explicit
allowlist when you enable network access.
:::

Allowlist entries must be one of `host`, `*.host`, an IPv4 address, or a CIDR
block, each optionally suffixed with `:port`. For example:

```bash
LANGFLOW_SANDBOX_ALLOW_NETWORK=true
LANGFLOW_SANDBOX_ALLOWED_DOMAINS=pypi.org,*.pythonhosted.org
```

Two rules are enforced strictly, both to keep the policy honest:

* IPv6 addresses and `*:port` are **rejected**. The platform cannot enforce
  either, and a rule it cannot enforce would silently match nothing.
* A malformed entry — a non-numeric or out-of-range port such as
  `pypi.org:https` — **refuses the run**. It is not sent, because the platform
  responds to a rule set it cannot parse by allowing all traffic.

:::note
When an allowlist is set, a public DNS resolver is added so names can be
resolved at all. That resolver answers for any name, so a sandbox can still
*resolve* hosts it cannot *reach*. DNS therefore remains a low-bandwidth
exfiltration channel under this backend. The `exec-sandbox` backend filters DNS
inside the guest and does not have this property.
:::

## Packages in the guest

The sandbox has no network by default, so the guest cannot install anything at
run time. Whatever the rootfs image ships is all the code gets.

To add packages, build a CreateOS template and name it in
`CREATEOS_SANDBOX_ROOTFS`:

```bash
curl -X POST https://api.sb.createos.sh/v1/templates \
  -H "X-Api-Key: $CREATEOS_SANDBOX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "langflow-python",
    "dockerfile": "FROM nodeops/sandbox:debian\nRUN pip install --no-cache-dir numpy pandas matplotlib"
  }'
```

```bash
export CREATEOS_SANDBOX_ROOTFS=langflow-python
```

Template Dockerfiles must be single-stage, must start `FROM` an allowlisted base
image, and must not use `COPY` or `ADD`. Poll `GET /v1/templates/{id}` until the
status is `ready`. The name resolves to the newest ready template, so rebuilding
under the same name updates new sandboxes automatically.

## Sessions

By default every execution gets its own VM and nothing carries over. Set
`LANGFLOW_SANDBOX_SESSION_MODE=flow` to reuse one guest across executions of the
same flow by the same user:

```bash
export LANGFLOW_SANDBOX_SESSION_MODE=flow
export LANGFLOW_SANDBOX_SESSION_IDLE_SECONDS=600
```

What carries over:

* Variables and imports defined at the top level of your code.
* Files written anywhere under `/workspace`, except the artifact directory,
  which is emptied before each execution.

What this is for: an agent that runs many small snippets. Each execution after
the first skips VM creation, and the agent can build on what it computed last
time instead of starting from nothing.

Reusing a guest keeps its filesystem, not its Python process. Each execution is
still a fresh interpreter, so Langflow carries the variables across by saving
them in the guest when the program ends and restoring them when the next one
starts. Only values that can be pickled survive. An open file handle, a socket,
or a lambda is dropped, and so is any single value over 4 MiB.

:::warning Reuse weakens isolation between executions
The boundary between the guest and the Langflow host is unchanged. What changes
is the boundary between two executions of the same flow: code from one run can
read what earlier code left behind, in variables and on disk.

The session is keyed on the flow **and** the user, so two users of the same flow
never share a guest, and a caller without both identities gets no session at
all. Even so, leave this `off` unless the flow's executions are meant to trust
each other.
:::

A session guest is destroyed after `LANGFLOW_SANDBOX_SESSION_IDLE_SECONDS` of
inactivity, when Langflow shuts down, when an execution fails in a way that
leaves the guest's state unknown, or when an execution times out. Idle sessions
are reaped on the way into the next execution, so a process that stops running
code entirely leaves its last guests to the CreateOS auto-pause backstop
instead.

A timeout destroys the guest. Langflow enforces the deadline by closing the
connection, and the server kills the guest command when it next heartbeats, but
neither step is confirmed back to Langflow. A guest that might still be running
the previous program is not safe to reuse, so the session starts again from a
clean VM and its state is lost. Raise `LANGFLOW_SANDBOX_TIMEOUT_SECONDS` if
legitimate work is being cut off.

### Sessions across workers

Langflow runs more than one worker, and each has its own memory. The session
guest is therefore registered with CreateOS rather than only in the worker that
made it: it is created under a name derived from the session token, and because
a sandbox name is unique per account among non-terminal sandboxes, the first
worker to create it wins and every other worker adopts that same guest.

So one flow has one guest per user, whichever worker takes the request, and you
are billed for one. This works across replicas as long as they share a CreateOS
API key.

:::warning Overlapping executions are not serialized across workers
Executions of one session are serialized within a worker. Two that overlap on
different workers are not: they share one guest, so they see each other's
variables and files partway through.

Each execution uploads its program under its own name and the state file is
replaced atomically, so neither can corrupt the other. The result is still
last-writer-wins on any variable both touch. Enable `flow` sessions only where
executions of one flow either do not overlap or tolerate sharing.
:::

The guest is **not** paused between executions. Measured on the live control
plane at the `s-2vcpu-4gb` default, pausing a guest takes 16.2 s and resuming
one takes 12.7 s, against about 1.0 s to create a fresh VM. Pausing an idle
session would therefore cost more than throwing it away.

## Artifacts

Set `LANGFLOW_SANDBOX_COLLECT_ARTIFACTS=true` to get files back out of the
guest. Anything the code writes to `/workspace/artifacts` is returned with the
result:

```python
from pathlib import Path
Path("/workspace/artifacts").mkdir(parents=True, exist_ok=True)
Path("/workspace/artifacts/report.csv").write_text("a,b\n1,2\n")
print("done")
```

The Python Interpreter component then returns an `artifacts` list beside
`result`, each entry holding `name`, `size`, and `content_base64`.

The directory is emptied before every execution, so a run only ever returns its
own files. Artifacts travel base64-encoded inside the component output, which is
why the default cap is small.

The guest chooses what it writes, so collection is bounded on three axes:
`LANGFLOW_SANDBOX_MAX_ARTIFACT_BYTES` (5 MiB by default) caps the extracted
content, the same number caps the compressed archive as it is downloaded, and
at most 256 entries are read. An archive over any of those limits is dropped
whole rather than truncated, and the execution's own result is returned
unchanged.

The legacy Python REPL **tool** does not collect artifacts. It returns one
observation string to a model, with nowhere to put a file.

## Timeouts

`LANGFLOW_SANDBOX_TIMEOUT_SECONDS` bounds how long Langflow waits. The CreateOS
execution endpoint has no server-side timeout, so Langflow runs the program over
a streaming connection and enforces the deadline by closing that connection. The
server heartbeats every 5 seconds, notices the client is gone, and kills the
guest command. A timed-out execution reports the same result as it would under
`exec-sandbox`, and it keeps whatever the program had already printed.

A margin is added for network transport, scaled to the configured value, so a
short timeout is not multiplied into a long wait. Treat the setting as a close
bound rather than an exact one: the margin, the upload, and VM teardown are not
inside it.

## What this backend does and does not give you

It gives you a kernel boundary between user-authored Python and the Langflow
host, for the two components listed above.

It does not make the sandbox unobservable or unable to signal outward. Link-local
is always reachable (see the warning above), and when you set a domain allowlist
a DNS resolver is reachable too, so code that wants to leak a small amount of
data still can.

It does not give you full multi-tenant isolation of Langflow itself. The
sandbox settings and the component-hardening flags are separate levers, and both
are described in [Security](./security.mdx).
