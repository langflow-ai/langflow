---
title: Review upgrade reports
slug: /upgrade-reports
---

Open **Settings > Upgrade reports** as an administrator and import the JSON file produced by `langflow upgrade-check` in the target release. The report is stored in the instance database and remains available after a reload. **Export original report** downloads the exact imported document, including additional metadata. Reports can contain private flow metadata and should be handled with the same care as database backups. The import limit is 20 MiB.

The page shows the source, target, report age, saved versions, deployments, findings, and retained execution history. Missing metadata stays unknown. Older reports may omit flows whose components were already current. The page identifies that incomplete coverage. An absent job record does not prove that a flow never ran. Editor and Serving history remain separate, with their observed periods and retention limits.

Select up to 100 flows and choose **Preview selected updates**. Preview checks current database contents with the installed target code and the owner's current policy. It does not trust replacement code from the report. A customized or unsafe flow remains for manual repair. A discovery check that could not verify an update remains distinct from confirmed data loss.

Before applying updates, make a current backup and enable database maintenance. The separate instance migration pause must be off. Review the preview and confirm the updates. The server checks the target and each flow again before writing. Concurrent changes require another preview. Each successful update retains an owner-visible recovery version. Saved outcomes show updates, refusals, conflicts, and recovery identifiers independently of the immutable imported report. Review those outcomes before retrying an interrupted request.

Report history is administrative evidence. It does not authenticate the source installation, prove that data stayed unchanged after the check, or certify an upgrade and restore route.

Account erasure deletes a report and its repair history when the report's creator or an owner is identified by the account's immutable ID. A matching owner name without a valid owner ID requires manual attribution review because names can be reused. The erase request remains **Erasing**, keeps the report and account, and stops automatic retries. Its error includes `report_owner_attribution_required`, `manual_review_required: true`, and the report ID. Earlier completed erase steps remain committed. Review the archive's owner attribution and resolve the ambiguity through the approved data-handling process before using the existing manual retry action. Retrying an unchanged archive does not bypass the review requirement.
