Run `langflow upgrade-check` from the release you are upgrading to, before you upgrade the server. The command reads that server's database and names every saved flow that needs action, without changing the database.

Import the report under **Settings > Upgrade reports**, preview the flows you select, and apply the safe updates during maintenance.

The command checks every flow, saved component, and saved flow version that a trigger pins or a deployment runs.
Starter projects are skipped.

For each node, the report gives a status, a dry run of the visual editor's **Update**, and what the upgraded server runs for that node. The dry run rebuilds the node from the new release with its saved values. Nothing is saved.

| Node status | Meaning |
|---|---|
| `ok` | The node matches this release. |
| `outdated_safe` | An update keeps every connection and saved value. |
| `outdated_breaking` | An update would drop a connection or a saved value, or needs an input the flow does not have. |
| `retired` | The component was retired and fails when the flow runs. |
| `customized` | The component's code was edited, or an update was dismissed in the visual editor. |
| `blocked` | The component type is not in this release. |
| `could_not_verify` | Generated fields or saved file references could not be verified, and no breaking change was confirmed. |

A flow's status is the worst of its nodes:

- `fail`: a node is `outdated_breaking`, `retired`, or `blocked`, the upgraded server refuses to run a node, or a customized node's edits will not run because the server uses its own code.
- `warn`: a node is `customized` and its edits still run, a dry run is `could_not_verify`, or the new code for a node does not build. A flow whose saved data cannot be read also warns.
- `ok`: nothing needs action.

A confirmed failing finding stays `fail` when the same flow also has a warning.

The check does not run flows, migrate the database, or inspect files, knowledge bases, credentials, or variables. To check those, see [Migrate to a new Langflow instance](./instance-migration.mdx).

The report is not one snapshot. Flows are read in pages, and a flow saved during the check is read as it is when its page is reached. Each flow is judged as its owner runs it.

## Before you run the check

Pass the upgraded server's settings as options. The command does not read server settings from the environment or a `.env` file. The options are listed in [Configuration](#configuration).

If the database is SQLite, its folder must be writable. SQLite creates a `-shm` file next to the database even for a read. The database file itself does not change. A read-only Docker volume stops the command. Mount the folder writable, or stop the server and copy the database together with its WAL files into a writable folder. A WAL file can hold committed flows that are not yet in the main database file.

Write `--output` to a path that is not the SQLite database or its WAL, shared-memory, or journal files. The command refuses a path that aliases those files.

If the database is PostgreSQL, use a user that can only read, and install the `postgresql` extra or use the Docker image, which includes the driver.

```sql
CREATE ROLE langflow_check LOGIN PASSWORD 'CHANGE_ME';
GRANT CONNECT ON DATABASE langflow TO langflow_check;
GRANT USAGE ON SCHEMA public TO langflow_check;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO langflow_check;
```

Other users of the machine can see the database URL in the process list while the check runs.

## Run the check

The examples use Langflow 1.14.0. Replace that version with the release you upgrade to.

<Tabs>
<TabItem value="pip" label="pip or uvx" default>

Run the command with the new release, without installing it over the running server:

```bash
uvx --from "langflow[postgresql]==1.14.0" langflow upgrade-check \
  --database-url "postgresql://langflow_check:CHANGE_ME@db.example.com:5432/langflow" \
  --output upgrade-check.json
```

For a SQLite database, pass the absolute path of the file:

```bash
uvx --from "langflow==1.14.0" langflow upgrade-check \
  --database-url "sqlite:////var/lib/langflow/langflow.db" \
  --output upgrade-check.json
```

</TabItem>
<TabItem value="docker" label="Docker">

Mount the volume that holds the server's SQLite database, writable, and pass the path the server's `LANGFLOW_DATABASE_URL` names:

```bash
docker run --rm \
  -v langflow-data:/app/langflow \
  langflowai/langflow:1.14.0 \
  langflow upgrade-check \
    --database-url sqlite:////app/langflow/langflow.db \
    --json > upgrade-check.jsonl
```

For PostgreSQL, pass the database URL and no volume. With `--json`, a completed check ends with a report event. Save that event with the extraction command below.

</TabItem>
<TabItem value="kubernetes" label="Kubernetes">

1. Store the database URL in a secret:

    ```bash
    kubectl create secret generic langflow-upgrade-check \
      --namespace langflow \
      --from-literal=database-url="postgresql://langflow_check:CHANGE_ME@postgres:5432/langflow"
    ```

2. Create a Job that runs the new release's image:

    ```yaml
    apiVersion: batch/v1
    kind: Job
    metadata:
      name: langflow-upgrade-check
      namespace: langflow
    spec:
      backoffLimit: 0
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: upgrade-check
              image: langflowai/langflow:1.14.0
              command: ["langflow", "upgrade-check"]
              args: ["--database-url", "$(DATABASE_URL)", "--json"]
              env:
                - name: DATABASE_URL
                  valueFrom:
                    secretKeyRef:
                      name: langflow-upgrade-check
                      key: database-url
    ```

    `backoffLimit: 0` keeps Kubernetes from running the check again when it exits with `1`. If the server loads custom components, mount the same folders and add `--components-path` for each one.

3. After the Job reaches `Complete` or `Failed`, save its logs:

    ```bash
    kubectl logs job/langflow-upgrade-check --namespace langflow > upgrade-check.jsonl
    ```

    Exit `1` marks the Job as failed even though the check finished and produced a report that needs review. Exit `2` means the check could not finish. Keep the logs from either terminal state and inspect the final event.

</TabItem>
</Tabs>

For Docker or Kubernetes, extract the one report event from the saved logs. A check that could not finish has no report event, so extraction fails and leaves any existing report unchanged. A completed warning or failure report still has a report event. Non-JSON log lines are ignored.

```bash
report_tmp=$(mktemp ./upgrade-check.XXXXXX)
if jq -R -s -e '
  split("\n") | map(fromjson? | objects | select(.event == "report"))
  | if length == 1 and (.[0].report | type == "object") then .[0].report
    else error("expected exactly one report event") end
' upgrade-check.jsonl > "$report_tmp"; then
  mv -- "$report_tmp" upgrade-check.json
else
  rm -f -- "$report_tmp"
  false
fi
```

## Read the result

| Exit code | Meaning |
|---|---|
| `0` | Every checked flow is OK, and no source blocker was found. |
| `1` | At least one flow needs review, or the database has a problem that stops the upgraded server from starting. A report that contains only warnings also exits 1. |
| `2` | The check could not finish. The last line says what to change. |
| `130` or `143` | The check was stopped by `SIGINT` or `SIGTERM`. Run it again. |

Without `--json`, the command prints counts, then each failing or warning flow. With `--json`, each flow is one JSON object as soon as it is checked, and the last line is the report. If the check cannot finish, the last line is an error event instead. `--output` writes the report as one JSON file.

A node lists what it runs (`saved_code`, `server_code`, or `refused`) and a dry-run result of `keeps`, `loses`, `could_not_verify`, or `build_failed`.

Zero retained executions does not mean a flow never ran. Job retention can remove records. Editor and Serving history stay separate. To include Serving history, pass `--serving-database-url`. Saved components have no execution history. Saved flow versions reuse their owning flow's counts, and those counts are not specific to one version.

When a dry run cannot verify generated **Run Flow** or **MCP Tools** fields, the flow warns with `could_not_verify`. Review those fields in the editor before you upgrade. A confirmed removed field or a runtime refusal still makes the flow fail. A custom component whose update calls the network is also `could_not_verify`.

## Review the report {#review-the-report}

Open **Settings > Upgrade reports** as an administrator and import the JSON file. The report is stored in the instance database and remains available after a reload. **Export original report** downloads the imported document. Reports can contain private flow metadata. Handle them with the same care as database backups. The import limit is 20 MiB.

The page shows the source, target, report age, saved versions, deployments, findings, and retained execution history. Missing metadata stays unknown. Older reports can omit flows whose components were already current, and the page identifies that incomplete coverage. An absent job record does not prove that a flow never ran.

## Repair selected flows {#repair-selected-flows}

Select up to 100 flows and choose **Preview selected updates**. Preview reads the current database with the installed release and the flow owner's current policy. It does not use replacement code from the report. A customized or unsafe flow stays for manual repair. An update the checker could not verify stays separate from a confirmed loss.

Before you apply updates, back up the database and turn on [maintenance mode](./maintenance-mode.mdx). Stop incoming traffic and wait for admitted work to finish. The instance migration pause must be off. Review the preview, then confirm. The server checks the target and each flow again before it writes. If a flow changed after the preview, preview it again. Each successful update keeps a recovery version the owner can see.

Review the saved outcomes before you retry an interrupted request. Verify the repaired flows and the recovery versions before you reopen traffic. The imported report does not prove that the database stayed unchanged after the check, and it does not certify the upgrade.

## Configuration {#configuration}

Set these options to the values the upgraded server will use. A setting you omit takes the default in this table.

| Option | Matches | Default |
|---|---|---|
| `--database-url` | The database you are about to upgrade. Required. The command only reads it. | None |
| `--serving-database-url` | A separate Serving database, read with a read-only account. `job.flow_id` must still hold the Editor flow ID. | None |
| `--components-path` | `LANGFLOW_COMPONENTS_PATH`. Repeat the option for each folder. | None |
| `--discovery-timeout` | Seconds allowed to load installed and custom components. | `300` |
| `--allow-custom-components` / `--no-allow-custom-components` | `LANGFLOW_ALLOW_CUSTOM_COMPONENTS` | Allowed |
| `--substitute-outdated-component-code` / `--no-substitute-outdated-component-code` | `LANGFLOW_SUBSTITUTE_OUTDATED_COMPONENT_CODE` | On |
| `--block-code-interpreter-components` / `--no-block-code-interpreter-components` | `LANGFLOW_BLOCK_CODE_INTERPRETER_COMPONENTS` | Off |
| `--custom-component-admin-only` / `--no-custom-component-admin-only` | `LANGFLOW_CUSTOM_COMPONENT_ADMIN_ONLY` | On |
| `--allow-components-paths-override` / `--no-allow-components-paths-override` | `LANGFLOW_ALLOW_COMPONENTS_PATHS_OVERRIDE` | On |
| `--json` | Print JSON events instead of the text summary. Logs go to stderr. | Off |
| `--output` | Write the report to this JSON file. | None |

If the upgraded server loads custom components, pass every folder with `--components-path`. The command imports that code, so it needs the same Python packages as the server. With `--no-allow-custom-components` and `--no-allow-components-paths-override`, the command loads none of those folders.

On a busy machine, use `--discovery-timeout 600`. Each node's dry run still has a separate 30-second limit.
