---
title: Repair selected flows during maintenance
slug: /admin-flow-repairs
---

An active superuser can preview selected stored flows and apply verified safe updates during database maintenance.
The server selects replacement code from its installed component registry.
The request cannot supply a graph, component source, or a repair result.

## Preview selected flows

Send `POST /api/v1/upgrade-repairs/preview` with `flow_ids` and an optional imported `report_id`.
Each request selects between 1 and 100 distinct flow IDs.
The response contains the installed Langflow and LFX versions, a target registry fingerprint, and one result for each selected flow.
These installed versions describe the code used for repair, independently of an imported report's target metadata.
Preview does not change any flow or create a recovery version.

A ready result includes `flow_id`, `version_token`, `data_sha256`, and the number of nodes that can update.
Keep the exact values from preview for the apply request.
A legacy flow can have an explicit null token.
The digest still identifies the stored graph that the administrator reviewed.

## Apply the reviewed selection

Enable [database maintenance](./maintenance-mode.mdx), stop incoming traffic, and wait for admitted work to finish.
The API refuses repair while the job table contains running jobs.
The separate instance migration file pause always refuses repair, including superuser requests.
Maintenance authentication requires an existing API key or local JWT.

Send `POST /api/v1/upgrade-repairs/apply` with the preview's `target_sha256` and a `flows` array.
Each array entry contains only `flow_id`, `version_token`, and `data_sha256`.
An optional `report_id` links the server's results to imported report history.
The server checks the source graph and registry again before applying any update.

Each flow uses its own transaction.
A successful transaction creates an owner-visible retained recovery version, updates the graph, and records its report outcome together.
A failed transaction rolls back the graph, version token, and recovery entry.
Other selected flows still receive independent results.
Recovery versions are protected from normal history pruning and deletion.

The caller's authorization permits the cross-user write.
The stored owner's identity, project, workspace, and provider policy govern the component context.
Repair does not read provider credentials or execute saved component code.
Saved field values, global-variable references, and all nested edges must remain intact.
Nodes marked `edited=true` stay unchanged.

## Read the outcomes

| Status | Meaning |
| --- | --- |
| `ready` | Preview found safe updates for this flow. |
| `updated` | Apply committed the update and its retained recovery version. |
| `unchanged` | No eligible node needs an update. |
| `manual` | The server could not prove preservation or requires a separate repair procedure. |
| `conflict` | The reviewed source changed or the database was busy. Preview again. |
| `forbidden` | Authorization refused the selected write. |
| `not_found` | The selected flow no longer exists. |
| `failed` | The repair transaction did not commit. |

Manual cases include locked flows, file-backed flows, missing owners, malformed graphs, duplicate node IDs, and breaking or unavailable component contracts.
File-backed flows require a separate update of their external source files.
Dynamic fields whose update cannot be verified remain manual.
Delegated model inputs and provider overrides are checked under the stored owner's policy.
Unknown, malformed, connected, or global-variable provider selections return `provider_selection_unverifiable` and require manual review.
No input is hydrated to resolve that uncertainty.
The existing conservative static MCP classification still applies.
A missing prerequisite or unavailable database is reported as a failure rather than an authorization denial.

After repair, graph replacements require the flow's current `If-Match` token.
An older author session cannot overwrite the repaired graph by omitting the header.
A missing token returns `428`; a stale token returns `409`.
Reload the flow before saving again.
Metadata-only changes retain their existing behavior.

Verify repaired flows and retained recovery access before reopening normal traffic.
Local repair tests do not certify an upgrade or restore route with published release artifacts.
