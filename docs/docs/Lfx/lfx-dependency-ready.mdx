# Dependency-ready Python graphs

`Graph.arun()` and `Graph.process()` accept an optional `dag_max_concurrency` positive integer. When every component in a static graph explicitly supports dependency-ready scheduling, a completed branch can release its next component without waiting for an unrelated slow branch. The number of admitted component build tasks never exceeds the bound. `None`, the default, keeps the existing scheduler.

This is a Python component-author API, not a speedup automatically applied to saved UI flows. It does not add a frontend, HTTP, environment-variable, `async_start()`, or `astep()` option.

## Promise made by each component author

Declare `supports_dependency_ready_scheduling = True` directly on every concrete component class. Inheriting the declaration or adding it to an instance or exported template does not opt in a class.

An opted-in component promises:

- Static dependencies, materialized outputs, and no graph activation, stopping, checkpointing, or scheduling-state changes.
- No mutation of objects shared between independent branches that relies on their execution order.
- Ownership of all its work: await requests, callbacks, and framework thread work; do not detach background work or cancel the component task itself.

The declaration is an author contract, not an automatic proof of thread, client, or provider safety. In particular, modern Chat Input, Chat Output, and Language Model components are not opted in. Arbitrary provider clients, streaming callbacks, memory, and live output objects need their own ownership review.

The graph uses the existing scheduler if any vertex lacks the declaration or an existing instance, or if it contains cycles, state/loop/tool-mode nodes, frozen or streaming nodes, checkpoint/resume/pause state, or dynamic branch state. A graph with a previously built vertex or populated output cache also falls back. Deferred component instances are not constructed just to inspect eligibility. Custom Graph subclasses and custom coordinators keep their original execution path.

The selection is checked before any build starts. An unsupported graph runs once on the existing path; a graph that fails after dependency-ready execution begins is never retried on that path.

## Runnable local HTTP example

The following example makes real asynchronous HTTP requests to a controlled loopback service. It demonstrates adapter ownership and asymmetric branches, not the performance or safety of a commercial inference provider. Install `lfx` and `aiohttp`, save the code as `example.py`, then run `python example.py`.

```python
import asyncio
from aiohttp import ClientSession, web
from lfx.custom.custom_component.component import Component
from lfx.graph import Graph
from lfx.io import FloatInput, HandleInput, Output, StrInput
from lfx.schema.message import Message


class LocalInference(Component):
    supports_dependency_ready_scheduling = True
    inputs = [
        HandleInput(name="messages", input_types=["Message"], is_list=True),
        StrInput(name="endpoint"),
        FloatInput(name="latency", value=0),
    ]
    outputs = [Output(name="message", method="infer")]

    async def infer(self) -> Message:
        text = " ".join(m.text for m in (self.messages or [])) or "Document"
        async with ClientSession() as session:
            async with session.post(
                self.endpoint,
                json={"text": text, "id": self._id, "delay": self.latency},
            ) as response:
                response.raise_for_status()
                data = await response.json()
        # Response body consumed; response and session closed before returning.
        return Message(text=data["text"])


async def main():
    async def infer(request):
        data = await request.json()
        await asyncio.sleep(data["delay"])
        return web.json_response({"text": data["text"] + "|" + data["id"]})

    app = web.Application()
    app.router.add_post("/infer", infer)
    runner = web.AppRunner(app)
    await runner.setup()
    site = web.TCPSite(runner, "127.0.0.1", 0)
    await site.start()
    port = site._server.sockets[0].getsockname()[1]
    endpoint = f"http://127.0.0.1:{port}/infer"
    try:
        delays = {"input": 0, "a1": .25, "a2": .01,
                  "b1": .01, "b2": .25, "join": 0, "out": 0}
        nodes = {key: LocalInference(_id=key, endpoint=endpoint, latency=delay)
                 for key, delay in delays.items()}
        dependencies = {"a1": ["input"], "a2": ["a1"], "b1": ["input"],
                        "b2": ["b1"], "join": ["a2", "b2"], "out": ["join"]}
        for key, parents in dependencies.items():
            nodes[key].set(messages=[nodes[parent].infer for parent in parents])
        graph = Graph(nodes["input"], nodes["out"])
        await graph.arun(inputs=[{}], outputs=["out"], dag_max_concurrency=2)
        print(graph.get_vertex("out").built_object["message"].text)
    finally:
        await runner.cleanup()


asyncio.run(main())
```

Create a new graph to compare scheduling policies. Reusing a built graph can reuse cached output through the existing execution path and is not a valid performance comparison.

## Completion events and ordering

Results are recorded using the existing persistence gates. For each completed vertex, result handling and the attempt to emit its complete vertex event finish before a descendant is admitted. Event-handler errors retain the existing behavior: ordinary errors are logged and swallowed, and missing backend imports are ignored. Awaiting the helper means the emission attempt ended, not that a client received it.

Under this option, `next_vertices_ids` means newly dependency-ready successors. These vertices can wait in the queue when capacity is full. Independent completion events can arrive in a different order from layer execution. Final output collection still follows graph vertex order.

## Cancellation and failures

:::warning Natural drainage can wait indefinitely

Cancellation or a component failure stops new admission. It does **not** cancel already admitted build tasks. The invocation waits for all admitted tasks, including framework-awaited synchronous thread work, to finish naturally before it returns or raises. An uncooperative component can therefore make cancellation wait indefinitely. There is no timeout that abandons its workers.

:::

The first observed outer cancellation or selected component failure wins. Failures in the same observed completion group use graph order. If a group contains a failure, successful siblings in that group are drained but their graph-level results are not persisted or emitted. Later cancellation cannot replace an earlier failure, and all admitted outcomes are retrieved. Unadmitted descendants do not run after an aborted invocation.

For an eligible run, direct `process()` owns trace finalization. `arun()` owns it through output collection. The non-subgraph owner attempts and awaits run-level trace finalization once, including the native tracer's flush, while preserving a primary error over cleanup errors. Subgraphs retain parent-owned traces. Requested-but-unsupported graphs keep their existing cleanup behavior.

Self-cancellation and detached component work violate the capability promise. Siblings are still drained and run-level finalization is attempted, but this is not a guarantee that every arbitrary provider resource or component span closes. A remote request already accepted by a service is not remotely cancelled by this option.

## Measuring usefulness

From a source checkout with the lfx development environment installed:

```bash
python scripts/benchmark/dag_scheduler.py --pairs 7 --output /tmp/dag-scheduler.json
```

The harness creates fresh graphs, warms up both policies, then alternates seven baseline/opt-in pairs for asymmetric, reversed, balanced, tiny, and wide workflows. It records raw component and HTTP timelines, end-to-end latency, first component completion, admitted concurrency, HTTP requests, traced peak memory, and output digests. All requests use a deterministic local HTTP service with controlled latency. This is scheduling evidence, not an inference quality or provider throughput benchmark. `tracemalloc` affects timing.

One Python 3.13.16 Linux run of the implementation above, with seven pairs per workflow, measured these medians in milliseconds:

| Workflow | Existing scheduler | Dependency-ready |
| --- | ---: | ---: |
| Asymmetric | 521.73 | 277.74 (bound 2) |
| Reversed | 521.62 | 277.73 (bound 2) |
| Balanced | 279.86 | 277.98 (bound 2) |
| Tiny | 14.31 | 14.29 (bound 2) |
| Wide | 40.46 | 51.23 (bound 8) |

Each pair produced equal output digests, with no active HTTP or component work at return. The wide baseline admitted 16 branches versus the opt-in bound of 8, so that row measures a concurrency/memory tradeoff rather than an equal-concurrency speed comparison. The seven balanced opt-in observations ranged from 276.90 to 282.99 ms. These results show why this is opt-in: asymmetric dependency chains can benefit, but uniform workloads need not become faster.
