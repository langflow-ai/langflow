---
title: Start components when their inputs are ready
slug: /lfx-dependency-ready
---

LFX normally runs a graph one layer at a time. Every component in a layer finishes before any component in the next layer starts. A fast branch waits for a slow branch that shares its layer.

Pass `dag_max_concurrency` when you want a component to start as soon as its own inputs are ready, while an unrelated branch is still running. The value is the maximum number of components that run at the same time.

Use this when you build a `Graph` in Python and call `Graph.arun()` or `Graph.process()`. [`lfx run`](./lfx-run) and [`lfx serve`](./lfx-serve) do _not_ accept `dag_max_concurrency`. Omit the argument, or pass `None`, and those Python calls keep the layer-by-layer scheduler too.

## Run a graph

Every component class in the graph must opt in, as described in the next section. Call either method with a positive integer:

```python
await graph.arun(inputs=[{}], outputs=["out"], dag_max_concurrency=2)
```

```python
await graph.process(fallback_to_env_vars=False, dag_max_concurrency=2)
```

Any other value raises `ValueError`. LFX decides whether the graph is eligible before the first component starts. If an eligible run fails after that, LFX does not run the graph again with the layer-by-layer scheduler.

Create a new `Graph` for each run you want to compare. After a graph has run, cached outputs make the next call use the layer-by-layer scheduler.

## Opt in each component

To opt in, set `supports_dependency_ready_scheduling = True` in the component class.
A value inherited from a base class, assigned on an instance, or stored in an exported template does not opt that class in.

```python
from lfx.custom.custom_component.component import Component

class LocalInference(Component):
    supports_dependency_ready_scheduling = True
```

Setting the attribute means all of the following are true:

- Dependencies are fixed before the run, and each output is a finished value. A component configured to stream is not eligible. If an opted-in component returns a stream, an iterator, or an awaitable anyway, the run fails.
- The component does not activate, stop, checkpoint, pause, or otherwise change how the graph is scheduled.
- The component does not change an object shared with another branch in a way that requires one branch to run first.
- The component finishes its own work before it returns. Await HTTP requests, callbacks, and thread work the framework hands you. Do not leave a task running after the method returns, and do not cancel the component's own task.

LFX does not check that your clients or provider libraries are safe to run at the same time. Chat Input, Chat Output, and Language Model are not opted in. A graph that includes one of them keeps the layer-by-layer scheduler.

## Run a graph with a local HTTP service

This graph splits into two branches. Branch A is slow, and then fast. Branch B is fast, and then slow. With `dag_max_concurrency=2`, the fast step on each branch runs while the slow step on the other branch is still in progress, so the two slow steps overlap.

Install `lfx` and `aiohttp`. Save the code as `example.py`, then run `python example.py`. The process prints one line, the text from the final component.

```python
import asyncio

from aiohttp import ClientSession, web

from lfx.custom.custom_component.component import Component
from lfx.graph import Graph
from lfx.io import FloatInput, HandleInput, Output, StrInput
from lfx.schema.message import Message


class LocalInference(Component):
    supports_dependency_ready_scheduling = True
    inputs = [
        HandleInput(name="messages", input_types=["Message"], is_list=True),
        StrInput(name="endpoint"),
        FloatInput(name="latency", value=0),
    ]
    outputs = [Output(name="message", method="infer")]

    async def infer(self) -> Message:
        text = " ".join(message.text for message in (self.messages or [])) or "Document"
        async with ClientSession() as session:
            async with session.post(
                self.endpoint,
                json={"text": text, "id": self._id, "delay": self.latency},
            ) as response:
                response.raise_for_status()
                data = await response.json()
        # The response body is consumed, and the response and session are closed.
        return Message(text=data["text"])


async def main():
    async def infer(request):
        data = await request.json()
        await asyncio.sleep(data["delay"])
        return web.json_response({"text": data["text"] + "|" + data["id"]})

    app = web.Application()
    app.router.add_post("/infer", infer)
    runner = web.AppRunner(app)
    await runner.setup()
    site = web.TCPSite(runner, "127.0.0.1", 0)
    await site.start()
    port = site._server.sockets[0].getsockname()[1]
    endpoint = f"http://127.0.0.1:{port}/infer"

    try:
        # Branch A is slow, then fast. Branch B is fast, then slow.
        delays = {
            "input": 0,
            "a1": 0.25,
            "a2": 0.01,
            "b1": 0.01,
            "b2": 0.25,
            "join": 0,
            "out": 0,
        }
        nodes = {
            key: LocalInference(_id=key, endpoint=endpoint, latency=delay)
            for key, delay in delays.items()
        }
        dependencies = {
            "a1": ["input"],
            "a2": ["a1"],
            "b1": ["input"],
            "b2": ["b1"],
            "join": ["a2", "b2"],
            "out": ["join"],
        }
        for key, parents in dependencies.items():
            nodes[key].set(messages=[nodes[parent].infer for parent in parents])

        graph = Graph(nodes["input"], nodes["out"])
        await graph.arun(inputs=[{}], outputs=["out"], dag_max_concurrency=2)
        print(graph.get_vertex("out").built_object["message"].text)
    finally:
        await runner.cleanup()


asyncio.run(main())
```

`infer` closes the HTTP session before it returns. Follow that pattern in your own components. The delays show the branches overlapping on your machine.

LFX uses the existing layer-by-layer scheduler for any of these cases:

- A component class is missing `supports_dependency_ready_scheduling = True`, or the vertex does not already hold a component instance. LFX does not construct a deferred component just to check.
- The graph contains a cycle, or a component that uses state, a loop, tool mode, or a frozen node.
- The run checkpoints, resumes, or pauses, or a conditional branch has already activated, stopped, or excluded vertices.
- A vertex was already built, or a component output is already cached.
- The graph is a subclass of `Graph`, or the run uses a custom coordinator. `Graph.arun()` logs a warning that `dag_max_concurrency` was ignored.

## Stop a run or handle a failure

:::warning Cancellation waits for components that already started

Cancelling the run, or a component raising an error, stops LFX from starting more components. Components that have already started keep running, including synchronous work on a worker thread. The call returns after those components finish. If one of them never finishes, the call waits. There is no timeout.

:::

When several components finish together and one of them failed, the reported error is the error that comes first in graph order. The other components in that group finish, and LFX discards their results. Components that had not started do not run. Cancelling after a component has already failed still reports that failure.

A request that a remote service has already accepted keeps running on that service.

If a component cancels its own task, or leaves work running after it returns, components that already started still finish. Connections and tracing spans from the detached work can stay open. For a top-level graph, LFX finishes run-level tracing before the call returns. A subgraph keeps the trace owned by its parent. If that cleanup fails, you still see the original component error.

## Read results and completion events

LFX saves each result the same way it does for a layer-by-layer run. It finishes saving a component, and it attempts that component's completion event, before it starts a component that depends on the result.

On this path, `next_vertices_ids` lists successors that just became ready. Those successors can wait when `dag_max_concurrency` components are already running. Independent branches can finish in a different order than in a layer-by-layer run. The outputs you requested are still collected in graph vertex order.

An error in an event handler is logged, and the run continues, as in a layer-by-layer run. Waiting for the handler means LFX finished the attempt. It does not mean a client received the event.
