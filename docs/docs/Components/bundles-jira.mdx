The **Jira Cloud** components provide five issue actions and three polling triggers.
Each component uses a [Connection](./connections) to one Jira Cloud site.
Create that Connection in **Settings**. The flow stores the handle, such as `jira/work`.
An exported flow keeps the handle. The credential stays on the server.
These components are in preview.

<GraduatedBundleInstall packageName="jira" />

To use the components, confirm where they run, configure the Atlassian app, create a Connection, and then add a component to a flow.

## Supported contexts

| Context | Actions | Triggers | Authentication |
| --- | --- | --- | --- |
| Self-managed Langflow with Jira Cloud | Preview | Preview polling | Customer-owned confidential OAuth 2.0 registration |
| Hosted Langflow with Jira Cloud | Preview | Unsupported | Operator-configured confidential OAuth 2.0 registration |
| Langflow Desktop | Unsupported | Unsupported | Jira public-client OAuth is not implemented |
| Headless `lfx run` or `lfx serve` | Unsupported | Unsupported | Environment tokens cannot establish the required managed site grant |
| Jira Data Center or Server | Unsupported | Unsupported | Only the Jira Cloud REST API v3 adapter is available |

Use a Langflow 1.14 server with the matching `lfx-jira` bundle installed in its Python environment.
Restart the API and listener processes after installing the bundle, and confirm it appears in `lfx extension list`.
Importing the bundle in standalone lfx does not make Jira execution supported there.

## Configure the Atlassian app

The server operator configures the OAuth application once.
Flow authors then connect their accounts through Langflow.
Atlassian recommends a single distributable integration instead of asking every end user to create an app or provide a token.
For more information, see [Atlassian's OAuth 2.0 setup and distribution guide](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/).

To configure the app, do the following:

1. Open the [Atlassian developer console](https://developer.atlassian.com/console/myapps/).
   Choose **Create**, then **OAuth 2.0 integration**, and name the app.
2. Choose the app's access type or grant type for delegated user access.
   Atlassian offers account-level grants and resource-level grants limited to selected sites.
   In either case, Langflow accepts only the configured site and verifies it during consent and refresh.
3. Under **Authorization**, configure **OAuth 2.0 (3LO)**.
   Set the callback to `https://YOUR_LANGFLOW_HOST/api/v1/connections/oauth/jira/callback` and save it.
4. Under **Permissions**, add the **Jira API** and configure the classic scopes `read:jira-work`, `write:jira-work`, and `read:jira-user`.
   Langflow also requests `offline_access` during consent to obtain refresh tokens.
5. Under **Settings**, copy the client ID and client secret into the server's secret configuration.
6. Find the Jira Cloud site UUID.
   Open `https://YOUR_SITE.atlassian.net/_edge/tenant_info` and copy the `cloudId` value.
   This is the site's UUID, not its URL, organization ID, or project key.
   You can also find it after `/s/` in the site's Atlassian Administration URL.
   For more information, see [Atlassian's Cloud ID instructions](https://support.atlassian.com/jira/kb/retrieve-my-atlassian-sites-cloud-id/).
7. Set `LANGFLOW_JIRA_CLOUD_ID` to the canonical lowercase site UUID.
   Use the same UUID in `tenant` and `allowed_tenants`.
   Replace all placeholders, then load this object into `LANGFLOW_CONNECTION_OAUTH_REGISTRATIONS` through your deployment's secret manager.

   ```json
   {
     "jira-work": {
       "provider": "jira",
       "profile": "user",
       "owner": "customer",
       "context": "self_managed",
       "client_type": "confidential",
       "client_id": "YOUR_CLIENT_ID",
       "client_secret": "YOUR_CLIENT_SECRET",
       "redirect_uri": "https://YOUR_LANGFLOW_HOST/api/v1/connections/oauth/jira/callback",
       "tenant": "YOUR_CLOUD_UUID",
       "allowed_tenants": ["YOUR_CLOUD_UUID"],
       "scopes": ["read:jira-work", "write:jira-work", "read:jira-user", "offline_access"]
     }
   }
   ```

   The registration must include all four scopes, even when users only request read actions.
   The callback must match Atlassian's configured callback exactly, including its hostname, port, and path.
   Keep client secrets outside flow inputs, global variables, and frontend configuration.
8. Configure the API and every listener with the same site UUID, OAuth registration, database, and `LANGFLOW_SECRET_KEY`.
   For a hosted server, set the registration's `context` and `LANGFLOW_CONNECTION_OAUTH_CONTEXT` to `hosted`.
   A Langflow-owned hosted registration also requires `LANGFLOW_CONNECTION_OAUTH_HOSTED_ENABLED=true`.
   For more information, see [Configure connection OAuth](./connection-oauth).
9. Before other users authorize the app, enable sharing under **Distribution** and complete any required Atlassian approval.
   Start user consent from Langflow so its callback can validate the request.

The server verifies the site through Atlassian's accessible-resources API and reads the active account from that site's account API.

## Create a Connection and run actions

All Connections require `read:jira-user`, `read:jira-work`, and `offline_access`.
Write actions also require `write:jira-work`.
The account's Jira project permissions and issue security restrictions still apply.

To create a Connection and run an action, do the following:

1. Create a Jira Cloud Connection with [Add a connection](./connections?integration=jira#add-a-connection).
   Select the **Jira Cloud** tab.
   Every saved Jira Connection needs a refresh token, including action-only Connections.
   If consent returns no refresh token, Langflow asks for `offline_access` and removes a failed new Connection.
   A failed reconnect preserves the existing Connection for another attempt.
2. Add a Jira action to a flow and select that Connection.
3. Start with **Jira: Read Issue** and a visible issue key, such as `DEMO-123`, to confirm the Connection and project access.
4. For a write, use uppercase project keys and positive numeric IDs for issue types, statuses, and transitions.
   A summary can be up to 255 UTF-8 bytes, and a description can be up to 32768 UTF-8 bytes.
   Descriptions are converted to Atlassian Document Format.
   An empty description on update leaves the existing description unchanged.

Required custom fields, arbitrary field updates, attachments, deletion, and unrestricted JQL are outside this preview.
Choose a project and issue type whose required fields the component can supply.

## Enable polling triggers

Run `langflow listeners` alongside the self-managed API, or set `LANGFLOW_LISTENERS_MODE=subprocess` before starting Langflow.
For more information, see [Deploy Langflow trigger listeners](./deployment-trigger-listeners).
The listener needs outbound HTTPS access to Atlassian.
Public webhook ingress is not required.

To enable a trigger, do the following:

1. Add one of the three Jira triggers at the start of a flow you own.
   Select your own Jira Connection and enter **Project Key**.
   Shared and instance Connections cannot arm these triggers.
2. If necessary, enter a positive numeric **Issue Type ID** to narrow the project.
   A snapshot and its retained history must fit within 5000 distinct issue IDs.
3. Save the flow, then enable **Allow background runs** in the trigger node controls.
   You can also open **Settings**, **Connections**, and the Connection's **Actions** menu, then enable **Allow scheduled and deployed runs**.
   Both controls grant the same permission for this Connection.
4. Enable the trigger with its **Enabled** switch, or use **Resume** in **Settings**, **Triggers**.
5. Wait for the first complete poll to establish a baseline, then create or change a matching Jira issue.
   Open the trigger's event list to inspect the observed event and its run.

Polling defaults to 30 seconds and never runs faster than that minimum.
An operator can increase `LANGFLOW_LISTENER_POLL_INTERVAL_S`.
Provider rate limits, retries, and the time needed to scan a project can delay the next observation.

The first complete snapshot emits no events.
Later polls compare the project's latest visible issue state with the saved snapshot.
A created event requires a previously unseen issue created at or after the baseline began.
An older issue that becomes visible later does not produce a created event.
Update and status events require the issue to have been seen before.
Each trigger deduplicates events using the provider, project, immutable Jira issue ID, and observed version.

Jira triggers use authenticated polling only.
Do not configure Jira admin or dynamic webhooks for these components.
Pausing a trigger requires no remote webhook cleanup.
Polling works without public ingress on a supported self-managed server.

## Recover a Connection or trigger

| Symptom | Recovery |
| --- | --- |
| The Connection is expired or its Jira app access was removed | In **Settings**, **Connections**, open **Actions**, select **Reconnect**, and complete consent again. Then open **Settings**, **Triggers**, and select **Resume** for each affected trigger showing **Ready to resume**. Reconnect alone does not restart listening. |
| Background use is blocked | As the Connection owner, enable **Allow background runs** on the trigger or **Allow scheduled and deployed runs** on the Connection. Then resume the trigger. |
| The project exceeds 5000 issues or retained issue IDs | Set **Issue Type ID** to narrow the project, or choose a smaller project. Save, pause, and resume the trigger to establish a new baseline. |
| Jira is unavailable or rate limited | Keep the trigger active while the listener retries. Jira's `Retry-After` delay is honored. Check listener health if retries continue. |
| A scope or project permission is missing | Reconnect with the required scopes, or ask the Jira administrator to grant the project permission. Resume any blocked triggers afterward. |
| An issue type requires extra fields or a transition is unavailable | Use a compatible issue type or a transition currently available for that issue and account. |

A listener restart or temporary outage preserves the committed snapshot, so the next successful poll compares against it.
Pausing and resuming starts a fresh baseline and does not replay the gap.
Use the trigger's event list to replay an event that Langflow already recorded.
Writes are not retried after an ambiguous network failure.
Check Jira before repeating a create, update, or transition whose outcome is uncertain.
